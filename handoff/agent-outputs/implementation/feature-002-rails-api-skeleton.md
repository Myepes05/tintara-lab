## Summary
Generated the API-only Rails 8.1.3.1 application at `apps/api` on PostgreSQL, skipping the components listed in D-063 and keeping Action Mailer, Solid Cache, Solid Queue, Brakeman and RuboCop. Development and test read the Postgres container credentials from the repository-root `.env` through dotenv, so nothing is duplicated or hard-coded; CI passes the same variables through the workflow environment. Solid Cache and Solid Queue were moved onto the primary database (D-052) by turning their standalone schema files into ordinary migrations and removing the separate connections. `GET /api/v1/health` was written spec-first and is the only endpoint, and `.github/workflows/api.yml` runs RuboCop and RSpec against a Postgres 18 service.

## Solid Cache and Solid Queue on the primary database (D-052)
Rails 8 generates three database entries in production (`primary`, `cache`, `queue`), keeps the cache and queue tables in `db/cache_schema.rb` and `db/queue_schema.rb`, and points Solid Queue at the `queue` connection. Exactly four changes undo that:
1. `config/database.yml` production declares a single connection taken from `DATABASE_URL`; the `cache:` and `queue:` entries with their `migrations_paths` are gone.
2. `config/cache.yml` production no longer sets `database: cache`, so Solid Cache uses the app's own connection.
3. `config/environments/production.rb` no longer sets `config.solid_queue.connects_to`.
4. `db/cache_schema.rb` and `db/queue_schema.rb` were copied verbatim into two migrations (`CreateSolidCacheTables`, `CreateSolidQueueTables`) and deleted, so their tables belong to the primary schema and appear in `db/schema.rb`.

Their contents were taken from the installed gems' own templates (`solid_cache-1.0.10/lib/generators/solid_cache/install/templates/db/cache_schema.rb` and `solid_queue-1.7.0/lib/generators/solid_queue/install/templates/db/queue_schema.rb`), so the tables match what the gems expect; only the array-bracket spacing was changed by `rubocop -a`.

In test, `config.active_job.queue_adapter = :test` means jobs are captured rather than enqueued, so no worker is needed. Development and test keep the Rails defaults for the cache store (`:memory_store` and `:null_store`); Solid Cache and Solid Queue are production-side, which is where D-052 applies.

## Deviations from the prompt
1. **`--skip-ci` was added to `rails new`.** Rails 8.1 generates `apps/api/.github/workflows/ci.yml` and `apps/api/.github/dependabot.yml`. GitHub only reads workflows from the repository root, so those files would never run, and the prompt puts a single root `.github/workflows/api.yml` in scope. I skipped them rather than commit a dead workflow. D-063 does not mention the generated CI files either way.
2. **`.gitignore` and `storage/`.** The prompt asks to confirm `apps/api/.gitignore` ignores `storage/`. Rails only adds that entry when Active Storage is present, and Active Storage is skipped (D-063), so no `storage/` directory or entry exists. The other required entries are there: `/config/*.key` (covers `master.key`), `/.env*`, `/log/*`, `/tmp/*`.
3. **`apps/api/tmp/.keep` is not tracked.** The root `.gitignore` (Feature 1) ignores `tmp/` at every level, which outranks the `!/tmp/.keep` negation in `apps/api/.gitignore` — git does not re-include files inside an excluded directory. This is harmless (Rails recreates `tmp/`, `tmp/cache`, `tmp/pids` on boot; the server and the specs were both verified) and I left the root `.gitignore` alone because it is out of scope. See the follow-ups.

## Questions for the owner
1. **D-052 and D-062 are still `Proposed` in the decision log.** Both are implemented here as the prompt instructed. If you accept them, the log entries should move to `Accepted`; D-063 is in the same position and should also record the `--skip-ci` note from deviation 1.
2. **`config/master.key` and `config/credentials.yml.enc`.** The generator created both; the key is ignored and only `credentials.yml.enc` is committed, which is the Rails convention. The encrypted file currently holds only the generated `secret_key_base`. The repository is readable by everyone (D-059), so please store the master key somewhere safe outside the repository — without it the credentials file cannot be read again, and it is not in git.
3. **Production `DATABASE_URL`.** `config/database.yml` production reads it and declares nothing else, so Solid Cache and Solid Queue will share that one database (D-052). Nothing else about deployment was touched.
4. **`handoff/learning/README.md` was not committed by me.** It already lists both chapters correctly, so nothing needed changing. It is currently an untracked file in the working tree, alongside the rest of this session's uncommitted handoff work (`CLAUDE.md` §7b, the four updated templates, `handoff/templates/learning-chapter.md`, the decision log and the status file).
